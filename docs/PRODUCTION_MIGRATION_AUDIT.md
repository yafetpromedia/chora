## 2. Review of `apps/api/scripts/migrate-existing-db.mjs`

**Current behavior (hardened):** (1) `prisma migrate diff … --script --exit-code`; (2) **abort if exit code `2` (non-empty diff)**; (3) only then `prisma migrate resolve --applied 20260530170000_schema_catchup`; (4) `prisma migrate status`.

### Remaining dangers / limits

1. **Still only marks one migration.** It resolves `20260530170000_schema_catchup` only. If `_prisma_migrations` lacks other folders, `migrate status` can still show pending rows, and a later `migrate deploy` may try to run `init` (`CREATE TYPE "UserRole"`) against an existing schema.
2. **Does not handle failed rows.** If a failed row exists (P3009), `migrate status` / `migrate deploy` block. The script does not inspect or resolve them.
3. **`migrate status` after resolve is informational.** Operators must still baseline every missing folder before trusting `migrate deploy`.
4. **Environment trust.** It runs against whatever `DATABASE_URL` is in the process env. There is no database-name allow/deny check and no backup requirement enforced in code.
5. **Uses `npx` with `shell: true`** and inherits full `env` (low risk; logs may echo URL on error).

**Historical note:** An earlier revision lacked `--exit-code` and could mark catch-up applied on a non-empty diff. That gate is now required. Still: **do not use this script on production as part of a code-only deploy**; use the manual restore-rehearsed commands in §7.

### Related hazard: `db-sync` falls back to `db push`
`apps/api/scripts/db-sync.mjs` / `.ps1` run `prisma migrate deploy` and, **on any failure, silently run `prisma db push`**:
```js
console.warn('migrate deploy failed — falling back to db push...');
run(['run', 'prisma:push']);
```
`db-bootstrap.*` calls `db-sync`. On production with a dirty history this converts a safe, loud failure into an unreviewed schema rewrite. **Never run `db:sync`, `db:setup`, `db:bootstrap`, `db:push`, `prisma:migrate:reset` on production.** (The API `Dockerfile` CMD is just `node dist/main.js`; it does not run migrations — good. Keep it that way.)

## 3. Known hazards for existing production `chora_db`

I cannot see `_prisma_migrations` in production; the following are what the repo history proves *can* exist.

### 3.1 Failed migration records
- The old chain could not apply cleanly on PostgreSQL (see 3.2–3.4), so a production DB that ever ran `migrate deploy` likely has one or more rows with `finished_at IS NULL AND rolled_back_at IS NULL`.
- Prisma then refuses further `migrate deploy` (**P3009**) until each failed row is resolved (`--rolled-back` or `--applied`).
- The files for those names have since been replaced with no-ops, so (a) checksums differ from the stored ones, and (b) `--rolled-back` followed by `deploy` would just apply an empty file (harmless), while `--applied` just records it.
- Prisma Postgres migrations are normally executed as one multi-statement script, so a failed file is usually rolled back as a unit — but **do not assume**; verify actual objects read-only.

### 3.2 `subscriptions` migration — school INSERT issue
Old `20260530160000_subscriptions` ended with:
```sql
INSERT INTO "Subscription" ("id","schoolId","plan",...) VALUES ('sub_demo_addis','school-addis','STARTER',...)
ON CONFLICT ("schoolId") DO NOTHING;
```
`ON CONFLICT` does **not** guard the foreign key. If `School` had no `school-addis` row (fresh DB, or prod without the demo school) the insert hits `Subscription_schoolId_fkey` → FK violation → migration fails and a failed row remains (the DB can also keep the `Plan` enum/`Subscription` table if not rolled back). The repair commit removed the INSERT. **Consequence for prod:** if the row exists as failed/applied with the *old* checksum, it will not equal the current file's checksum.

### 3.3 `LibraryResource` ordering
Old chain order: `20260602121500_library_audience` (`CREATE TYPE "LibraryAudience"…; ALTER TABLE "LibraryResource" ADD COLUMN "audience"…`) ran **before** `20260603120000_library` created `LibraryResource` → "relation does not exist" on any fresh/clean chain. Now both are no-ops; `LibraryAudience` (line 74) and `LibraryResource` (line 1699) are created in the catch-up, and FKs are added at the end. Hazard remaining: on a prod DB where an old partial run left `LibraryAudience` or `LibraryResource` behind, the catch-up's `CREATE TYPE/TABLE` will conflict (see 3.4/3.5).

### 3.4 Enum conflicts with `schema_catchup`
Catch-up has **57 `CREATE TYPE "…" AS ENUM`** with no `IF NOT EXISTS` (lines 5–173), e.g.:
```sql
CREATE TYPE "SchoolStaffRole" AS ENUM (...);
CREATE TYPE "LibraryAudience" AS ENUM ('STUDENTS', 'TEACHERS', 'BOTH');
```
Any enum already present (from `db push`, from a half-applied old mid-chain migration, or a previously partially-applied catch-up) → `type "X" already exists` (SQLSTATE 42710) → catch-up fails (P3018).
It also contains non-idempotent enum value additions (lines 183–187):
```sql
ALTER TYPE "AttendanceStatus" ADD VALUE 'excused';
ALTER TYPE "AttendanceStatus" ADD VALUE 'medical';
ALTER TYPE "UserRole" ADD VALUE 'staff';
```
These fail with "enum label already exists" on a DB already matching Prisma. The file itself warns that multiple `ADD VALUE` per migration is problematic on PG ≤ 11.

### 3.5 Catch-up failing on already-existing schema
**Guaranteed to fail** if applied via `migrate deploy` on a DB that already matches `schema.prisma`: first statement after the header is `CREATE TYPE "SchoolStaffRole"`; then `CREATE TABLE` ×110 (no `IF NOT EXISTS`; count of `IF NOT EXISTS` in the file: **0**), `CREATE INDEX` ×224, `ADD CONSTRAINT` ×233. The recovery doc says the same: *do not run `migrate deploy` of catch-up against a DB that already has the full schema*.

**Guaranteed to fail or lose data** if applied to a DB that is at "init→subscriptions" state *with rows* — see §5.

## 5. Operations that can DROP or rewrite data

All in `20260530170000_schema_catchup` (the only file with destructive statements; verified by grep for `DROP|TRUNCATE|DELETE FROM|INSERT INTO|UPDATE "`: only three hits):

```sql
DROP INDEX "AttendanceRecord_schoolId_studentId_date_key";   -- line 190
DROP INDEX "AttendanceRecord_schoolId_studentId_idx";        -- line 193
ALTER TABLE "AttendanceRecord" DROP COLUMN "studentId",      -- line 199  **DATA LOSS**
ADD COLUMN "periodNumber" INTEGER NOT NULL DEFAULT 0,
ADD COLUMN "reason" "AttendanceReason",
ADD COLUMN "studentProfileId" TEXT NOT NULL,                 -- no default: fails if rows exist
ADD COLUMN "subject" TEXT,
ADD COLUMN "updatedAt" TIMESTAMP(3) NOT NULL,                -- no default: fails if rows exist
ALTER COLUMN "date" SET DATA TYPE DATE;                      -- table rewrite; time-of-day truncated
```
```sql
ALTER TABLE "User" ADD COLUMN "phone" TEXT, ... ADD COLUMN "username" TEXT NOT NULL;  -- lines 249–252, no default
```

- `DROP COLUMN "studentId"` irreversibly deletes the old student linkage in `AttendanceRecord` (the new `studentProfileId` is NOT backfilled).
- `date` → `DATE` rewrites the table and drops time-of-day.
- `User.username NOT NULL` with no default, and the `AttendanceRecord` NOT NULL adds, make the catch-up **fail on any DB where `User`/`AttendanceRecord` already contain rows** (Postgres rejects the `ADD COLUMN … NOT NULL` without default on a non-empty table). That is the safety net against data loss on the NOT NULL path, but **the `DROP COLUMN` runs in the same ALTER statement** — if the table is empty the drop succeeds silently. If `AttendanceRecord` has rows, the statement errors and rolls back as a unit (verify on a restore).
- Other `ALTER`s are additive. FK `ON DELETE CASCADE` rules created by the catch-up mean *later* deletes of `School`/`User` cascade widely; not a migration-time hazard.
- Outside migrations: `prisma db push` (via `db-sync` fallback) can rewrite/drop columns if the schema diverges; Prisma refuses data-loss changes without `--accept-data-loss`, but still applies the rest.

**Conclusion:** catch-up must **never** be executed against `chora_db` with `migrate deploy`. It is only valid on an empty DB (fresh install) or must be *skipped via `resolve --applied`* on a DB whose schema is already equal to Prisma.

## 6. Theory: can the app run if schema matches Prisma but `_prisma_migrations` is dirty?

**Yes, in theory — the runtime does not read `_prisma_migrations`.**

- `PrismaClient` (`apps/api/src/prisma/prisma.service.ts`, `$connect` on init) only needs tables/columns/enums that match the generated client. Migration bookkeeping is used only by `prisma migrate *` commands.
- The API container starts with `node dist/main.js`, with no migrate step, so a dirty `_prisma_migrations` (failed rows, stale checksums, missing rows) will not stop the app.
- **Current startup hooks (as of `sync/production-hardening`):**
  - `PrismaService.onModuleInit` — `$connect()` only (no writes).
  - `PlatformAccessService.onModuleInit` — **read-only** cache refresh of platform role permissions.
  - `PermissionsService` — **does not** seed on startup (explicit bootstrap only).
  - `PlanCatalogService` — **does not** seed on startup; read paths use in-memory defaults when the catalog is empty (no writes).
  - `PlatformAuthService` — **does not** create a platform owner on startup (explicit bootstrap only).
  - See `docs/PRODUCTION_STARTUP_SAFETY.md`. Catalog/owner seeding is opt-in via `apps/api/scripts/runtime-bootstrap.mjs` and must **never** run as part of a code-only production deploy.
- **What breaks:** `prisma migrate deploy` (P3009 on failed rows; would try to run `init` if its row is absent), `migrate status`, future deployments, and any CI step running `migrate deploy`. Also `migrate dev` would detect modified-after-apply checksums and demand a reset (never run on prod).
- **Caveat:** "schema matches Prisma" must be *proven* (empty `migrate diff`), not assumed. Subtle drift (a missing index, nullable vs NOT NULL, enum values) can exist and only appear as runtime errors.
- **Checksum mismatch (verified on disposable DB, Prisma 6.19.3):** corrupting the checksum of an already-finished migration does **not** make `migrate status` or `migrate deploy` fail, and no checksum warning appeared in CLI output. Deploy is blocked by **P3009** (failed rows), not by stale finished checksums. Do not hand-edit checksums.

So the lowest-risk "make history clean" goal is a **bookkeeping-only** fix (resolve), validated on a restore, and only after proving an empty diff.

## 7. SAFE migration PLAN (for humans)

**Principles:** read-only first; every write step rehearsed on a restored copy; stop at the first surprise; never `deploy` the catch-up on a populated DB; never `db push`/`reset`/`db:sync` on production.

### Phase A — Freeze and backup (human-executed; write-only to a *file*)
```bash
# On the VPS, maintenance window. Stop writers (API) first or accept a consistent snapshot:
pg_dump -Fc -d chora_db -f /secure/backups/chora_db_pre_migrate_$(date +%Y%m%d_%H%M).dump
pg_restore --list /secure/backups/chora_db_pre_migrate_*.dump | head   # verify dump is readable
```
**Stop condition:** dump fails, is empty, or cannot be listed → do not continue.

### Phase B — Read-only inspection of production (SELECT only)
Run with `psql "postgresql://…/chora_db" -X` (read-only role preferred; wrap in `BEGIN READ ONLY;`).

```sql
-- B1. Does the history table exist, and what state is each row in?
SELECT migration_name, checksum, started_at, finished_at, rolled_back_at, applied_steps_count,
       left(logs, 200) AS logs_head
FROM _prisma_migrations ORDER BY started_at;

-- B2. Failed / in-progress rows only
SELECT migration_name, started_at, left(logs, 300)
FROM _prisma_migrations WHERE finished_at IS NULL AND rolled_back_at IS NULL;

-- B3. Which of the 50 repo names are missing from the DB table? (compare B1 output to the folder list in §1)

-- B4. Do the key objects exist? (schema-level proof)
SELECT count(*) AS tables FROM information_schema.tables WHERE table_schema='public' AND table_type='BASE TABLE';  -- expect ~119 (110 catch-up + 8 early tables + _prisma_migrations); approximate, diff is the real proof
SELECT count(*) AS enums  FROM pg_type t JOIN pg_namespace n ON n.oid=t.typnamespace WHERE n.nspname='public' AND t.typtype='e';  -- expect 60 (57 catch-up + UserRole/AttendanceStatus + Plan)
SELECT enumlabel FROM pg_enum e JOIN pg_type t ON t.oid=e.enumtypid WHERE t.typname IN ('UserRole','AttendanceStatus') ORDER BY 1;  -- expect 'staff','excused','medical' present
SELECT column_name, data_type, is_nullable FROM information_schema.columns
 WHERE table_name='AttendanceRecord' AND table_schema='public';  -- expect studentProfileId present, studentId ABSENT, date = date
SELECT to_regclass('"LibraryResource"'), to_regclass('"StudentProfile"'), to_regclass('"PlanCatalog"');

-- B5. Row counts that matter (confirms what a destructive migration would hit)
SELECT (SELECT count(*) FROM "School") schools, (SELECT count(*) FROM "User") users,
       (SELECT count(*) FROM "AttendanceRecord") attendance;
```

Read-only Prisma commands (these only read; point at a **restored copy** by preference):
```bash
cd apps/api
export DATABASE_URL='postgresql://…/chora_db?schema=public'   # or the restore copy
npx prisma migrate status
npx prisma migrate diff --from-url "$DATABASE_URL" --to-schema-datamodel prisma/schema.prisma --script --exit-code
echo "exit=$?"     # 0 = empty diff (matches), 2 = DIFFERENCES, 1 = error
```
**Stop conditions after Phase B:**
- Diff exit code ≠ 0 → schema does **not** match; do NOT resolve. Take the printed SQL to a restore copy, review it, and plan separately.
- B4 shows `AttendanceRecord.studentId` still exists or `studentProfileId` missing → DB is at an old state; catch-up path is required and is data-destructive. **STOP; escalate** (needs a hand-written data-preserving migration).
- Row counts > 0 in `User`/`AttendanceRecord` **and** the DB lacks the new columns → same STOP.

### Phase C — Rehearse on a disposable restore (never skip)
```bash
createdb chora_db_sim
pg_restore -d chora_db_sim /secure/backups/chora_db_pre_migrate_*.dump
export DATABASE_URL='postgresql://…/chora_db_sim?schema=public'
cd apps/api
npx prisma migrate diff --from-url "$DATABASE_URL" --to-schema-datamodel prisma/schema.prisma --script --exit-code   # must exit 0
npx prisma migrate status
```
Then handle the sim according to the state seen in B1 (decision table, §8). Re-run `migrate status` until it prints `Database schema is up to date!`, then run `npm run build` and smoke-test the API against the sim. Do this against a real `chora_db` dump, not `edu_os` (the recovery doc validated only `edu_os`).

### Phase D — Production, only if C was green and the sim steps are identical

**Gate:** Phase D is **history bookkeeping only**. If schema diff is **non-empty** (current eight-table `chora_db`), **STOP here** and follow `docs/PRODUCTION_DATABASE_RECOVERY_PLAN.md` §6 (`resolve --rolled-back` on failed `subscriptions`, then `migrate deploy` of the repaired chain). Do **not** `resolve --applied` to pretend missing objects exist.

Decision table (state from B1 → action) — **all rows below require schema diff empty**:

| `_prisma_migrations` state | Schema diff | Action |
|---|---|---|
| Table missing / empty (pure `db push` DB) | empty | Baseline **every** migration: `migrate resolve --applied <name>` for all 50 folders (use the loop below). Do **not** use only the single catch-up resolve. |
| `init`…`subscriptions` applied, catch-up missing, others anything | empty | `resolve --applied 20260530170000_schema_catchup`; then resolve each remaining folder that is missing/failed (see below). |
| Some rows **failed** (`finished_at IS NULL`) | empty | For each failed row: `migrate resolve --rolled-back <name>` (it is then re-applied as an empty file by `deploy`) **or** `--applied` — pick one consistently and rehearse it. |
| Row exists and is `finished_at NOT NULL` with an *old checksum* | empty | Leave it. Verified: Prisma 6.19.3 deploy/status tolerate stale finished checksums. Do **not** edit `_prisma_migrations` by hand. |
| Any state (including failed `subscriptions`, 7 empty app tables) | **non-empty** | **STOP.** Not Phase D. Use production recovery plan §6. |

Exact commands (production window, after backup and passing sim):
```bash
cd apps/api
export DATABASE_URL='postgresql://…/chora_db?schema=public'

# D1. Re-prove empty diff, fail hard otherwise
npx prisma migrate diff --from-url "$DATABASE_URL" --to-schema-datamodel prisma/schema.prisma --script --exit-code || { echo "DIFF NOT EMPTY - STOP"; exit 1; }

# D2. Resolve ONLY the folders the DB is missing / that are failed. Example for a DB with NO history:
for d in $(ls prisma/migrations | grep -E '^[0-9]{14}_'); do
  npx prisma migrate resolve --applied "$d" || { echo "resolve failed on $d - STOP"; exit 1; }
done
#   (For a DB whose first four are already applied, skip those names and resolve the catch-up + the 45 no-ops that are missing.)

# D3. Verify
npx prisma migrate status                  # expect: Database schema is up to date!
npx prisma migrate diff --from-url "$DATABASE_URL" --to-schema-datamodel prisma/schema.prisma --script --exit-code   # expect exit 0
```

### When to use which command
- **`migrate resolve --applied <name>`** — only when the schema objects for that migration are *already present* and the diff is empty. Bookkeeping only; changes nothing in the schema.
- **`migrate resolve --rolled-back <name>`** — for a *failed* row you intend to re-run with the **current** migration file. On the eight-table empty DB, this is required for `20260530160000_subscriptions` before deploy (rehearsed: current file has no `school-addis` INSERT). **Never** re-run `init` or catch-up on a **populated** DB.
- **`migrate deploy`** — (a) brand-new empty DB; (b) eight-table empty `chora_db` **after** `--rolled-back` on failed subscriptions (see recovery plan §6); (c) *future* additive migrations once history is clean and the diff is empty. **Never** deploy catch-up against a DB that **already** has the full schema (use Phase D resolve instead).
- **Never on prod:** `migrate dev`, `migrate reset`, `db push`, `db:sync`, `db:setup`, `db:bootstrap`, `scripts/migrate-existing-db.mjs` (no empty-diff gate).

### Rollback
Restore the Phase A dump (`pg_restore` into a fresh DB, repoint `DATABASE_URL`). Do not attempt down-migrations. `resolve` only edits `_prisma_migrations`; if it was wrong, restoring the dump (or deleting the wrongly-added rows, with approval) is the way back.

### Global stop conditions (any one halts the plan)
1. Backup missing/unverified. 2. Phase B diff exit code ≠ 0. 3. Old-state schema detected (`studentId` present, new columns/tables missing). 4. Any command prints `P3018`, `P3009` unexpectedly, "already exists", or "data loss". 5. Sim rehearsal differs from prod state. 6. `DATABASE_URL` database name is not exactly the intended one (`chora_db` for prod, `chora_db_sim` for rehearsal; never `edu_os`).
